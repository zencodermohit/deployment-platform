Review

Verdict

Read as a design-review submission, this is a good document. The spine is correct, and most people building this get at least two of the following wrong.

What was already right

  • Control plane / build plane split as the organizing principle, not an afterthought.
  • Treating repository code as hostile. Correct, and correctly identified as the central problem.
  • Immutable artifacts with pointer-swap rollback instead of rebuilding.
  • CloudFront → S3 directly, rather than proxying static assets through an application server.
  • Conditional DynamoDB writes for idempotency under at-least-once delivery.
  • An async API that returns a deploymentId and does not wait for the build.
The systemic issue

It is a narrative, not a specification. Every place it says “and then X happens” without naming the mechanism is exactly where the build stalls in week two. The architecture isn't wrong — it's under-determined.

What I'd change about the presentation

Cut the self-assessment section (“Architecture 8.5–9/10”). Scoring your own work reads as insecurity, and the architecture speaks for itself. Same for the repeated “the reviewer said” framing — state the decision and own it.

Review

Ten corrections

Ranked by how much pain each one causes if left unaddressed.

1. “Build Orchestrator” was an empty box

The diagram showed SQS → Build Orchestrator → Fargate. There is no such AWS service; it has to be built, and the choice is load-bearing. Lambda cannot consume an SQS message and wait for a five-minute build. That box became four named components — dispatcher, source fetcher, reconciler, sweeper — and filling it in is most of the real engineering.

2. SQS does not retry your build

Conceptual error

The dispatcher deletes the SQS message the moment RunTask succeeds. The build fails ten minutes later, long after the message is gone. SQS retries cover dispatch failures, not build failures — so the original failure diagram assumed recovery the system did not have.

Worse: nothing in the original design would ever notice a container that got OOM-killed. That deployment sits in BUILDING forever, and nothing errors — the UI just spins.

3. Edge routing was unspecified, and it's the hardest part

CloudFront has no idea what a deployment is. Mapping dep-abc.example.com to an S3 prefix takes a CloudFront Function reading the Host header against a KeyValueStore. Three traps come with it, all of which bite on day one — covered in §01.

4. The container was handed a GitHub token

Contradicts its own principle

The brief says assume postinstall is malicious — then has that same container clone the repository, which requires a credential granting read access to every repo the installation covers. A malicious preinstall exfiltrates it in under a second.

Fix: the trusted side fetches the tarball and hands over a 15-minute presigned S3 URL. The container never sees a token and never contacts GitHub.

5. .next/ is not a static artifact

Listed as an upload target alongside dist/ and build/. But next build produces a server — unless output: 'export' is set, there is nothing to put on S3. Leaving this ambiguous is how the project silently triples in scope. See §00.

6. Fargate has no timeout setting

Listed as a config knob under resource limits. It isn't one. Timeouts are enforced twice: a watchdog inside the container, plus an external StopTask, because a wedged container will not kill itself. Related: Fargate ephemeral storage has a 20 GiB floor — you cannot set it lower.

7. The network isolation diagram was aspirational

X-marks showed the build task blocked from internal services. In reality, a task with egress to npm has egress to the internet, and restricting it needs an egress proxy or Network Firewall (~$300/mo). The honest version is stronger anyway: isolation comes from the task having nothing worth reaching and no credential worth stealing.

8. There was no data model

A JSON blob, but no key schema, no GSIs, no access patterns. In DynamoDB the access patterns determine the table; designing it the other way round does not work. Two queries shape everything — see §02.

9. Terraform sliced by AWS service

vpc/, iam/, s3/, sqs/ groups resources by vendor taxonomy rather than by lifecycle. IAM roles belong with the thing they grant access to. Slice by stack — network, data, build, edge, app — so things that change together live together.

10. No cost model, no test strategy

The two questions any reviewer asks in the first five minutes. Both now have documents: §06 and §08.

00 · Scope

What is and isn't being built

Success is not feature count. It is whether the system demonstrates correct judgment on five specific problems: safe execution of untrusted code, asynchronous state management, idempotency under at-least-once delivery, immutable deployments, and reproducible infrastructure.

If the project demonstrates those five convincingly, it has succeeded with a small feature set. If it has many features and gets any of the five wrong, it has failed.

Supported frameworks

Detection is by convention, not magic. A project must produce a directory of static files.

FrameworkDetectionOutput
Vitevite in depsdist/
Create React Appreact-scripts in depsbuild/
Astro (static)astro in depsdist/
Next.jsnext and output: 'export'out/
Plain staticno build scriptrepo root

Anything else is rejected at validation time with a clear error, including Next.js without output: 'export'. Rejecting loudly beats guessing wrong — a platform that silently deploys an empty directory is worse than one that refuses.

Explicitly out of scope

Each is a defensible cut, not an oversight.

ExcludedWhy
Server-side renderingMeans request-time compute, a router, cold-start handling — and running untrusted code continuously rather than for ten bounded minutes. A different threat model entirely.
Serverless functionsSame reason. Interesting, but doubles the system.
Build cachingReal value only at scale we won't reach; adds cross-tenant cache-poisoning surface.
MonoreposLong tail of edge cases, near-zero learning value.
Teams, RBAC, billingProduct surface, not engineering substance.
Multi-regionCost, and nothing learned that single-region doesn't teach.
Custom user domainsPer-domain ACM issuance and validation flows. Phase 3 at earliest.

Success criteria

  • A fresh AWS account reaches a working system from terraform apply plus one image push.
  • Deploying a public Vite repo produces a working URL in under 3 minutes.
  • A repo whose postinstall attempts to read AWS credentials obtains nothing useful. Tested, not assumed.
  • Delivering the same SQS message twice produces exactly one build.
  • Killing a build container mid-run leaves the deployment FAILED, not stuck in BUILDING.
  • Rollback changes served content without running a build.
  • Always-on cost stays under $10/month; total spend stays inside the credit pool.
01 · Architecture

Mechanism, not intent

The trust boundary

There is exactly one security boundary in this system, and everything else is arranged around it.

Trusted · Control plane
  • API Gateway, Lambda
  • DynamoDB — source of truth
  • SQS + DLQ
  • GitHub App credentials
  • CloudFront KeyValueStore
  • Source-tarball fetcher
Boundary
Untrusted · Build plane
  • Ephemeral Fargate task
  • The user's repository
  • npm install — lifecycle scripts run
  • npm run build
  • no GitHub token
  • no DynamoDB access
  • write to ONE S3 prefix

Isolation does not come from firewall rules. It comes from the task having nothing worth reaching and no credential worth stealing. Assume the container is fully compromised on every build, then ask what the attacker gets. The answer must be: a shell in a throwaway sandbox with write access to one S3 prefix that is about to be sealed.

The retry problem

Automatic build retry is deliberately not implemented. A failing build usually fails deterministically; retrying burns credits to reach the same answer. Making retry a user action also keeps the failed attempt visible in history.

Edge routing

GET https://dep-abc123.example.com/about/
        |
        v
CloudFront Function  (viewer-request, sub-ms, NO network calls)
        +- read Host header      -> "dep-abc123.example.com"
        +- KeyValueStore.get(host) -> "projects/p-1/deployments/dep-abc123"
        +- URI ends "/" or no extension? -> append "index.html"
        +- rewrite URI -> /projects/p-1/deployments/dep-abc123/about/index.html
        |
        v
S3 origin  (REST endpoint + OAC; bucket stays fully private)
Three traps

1. S3 REST origins do not serve directory indexes. GET /about/ returns 403, not about/index.html. The website endpoint handles it but is HTTP-only and needs a public bucket — unacceptable. The function must append index.html itself.

2. SPA fallback needs a CloudFront custom error response mapping 403/404 → /index.html with status 200.

3. Wildcard certificates are single-level. *.example.com does not cover dep-abc.preview.example.com. Keep subdomains one level deep.

Where the active-deployment pointer lives

DynamoDB is the source of truth; the KeyValueStore is a materialized read replica for the edge. The original design said rollback “changes the pointer” without saying where it lives. It lives in both, and the ordering matters.

promote(projectId, deploymentId):
  1. verify deployment belongs to project and status == DEPLOYED
  2. DynamoDB:  DOMAIN#<host> -> activeDeploymentId, artifactPrefix   (truth)
  3. CloudFront KVS: PutKey(host, artifactPrefix)                     (edge)
  4. no invalidation needed - the prefix changed, so cache keys changed

Step 4 is the payoff of immutability. Because artifacts live at unique paths and are never overwritten, there is never a cache invalidation. Rollback is instant and free. If step 3 fails after step 2 the edge is stale — the sweeper reconciles it via kvsSyncedAt, and stating that is better than pretending the two writes are atomic.

State machine

QUEUED→ PROVISIONING→ BUILDING→ UPLOADING→ DEPLOYED
any non-terminal →FAILED QUEUED / PROVISIONING →CANCELLED

PROVISIONING is a real state, not bookkeeping: Fargate cold start is 30–60 seconds, and without it the UI shows “queued” while the user watches nothing happen for a minute.

FromToWritten byGuard

Idempotency in one sentence: the QUEUED → PROVISIONING conditional update is the claim, and DynamoDB guarantees exactly one writer wins it. The claim happens in the dispatcher, before RunTask — claiming inside the container would be too late, because two containers would already be running.

Networking

Build tasks run in a public subnet with a public IP and a zero-inbound security group; gateway VPC endpoints for S3 and DynamoDB (free). No NAT Gateway, no interface endpoints.

A public IP with no inbound rules is not exposed — nothing can initiate a connection to it. The build subnet has no route to anything internal because there is nothing internal: the control plane is entirely serverless and reachable only over authenticated public APIs.

Honest limitation

Egress is unrestricted. Limiting it to npm and GitHub needs an egress proxy or AWS Network Firewall at roughly $300/month. The mitigation is that outbound access buys an attacker nothing, because the container holds no credential worth exfiltrating. This is recorded as an accepted risk rather than drawn as a control that doesn't exist.

02 · Data model

Access patterns first

Single table, on-demand, PITR on, encrypted with a customer-managed KMS key. Two queries shape the whole design: “list deployments for a project, newest first” and “find in-flight deployments past their deadline”.

EntityPKSKGSI1GSI2
UserUSER#<id>PROFILEEMAIL#<email>—
ProjectUSER#<id>PROJECT#<id>PROJECT#<id>—
DeploymentPROJECT#<id>DEP#<createdAt>#<id>DEP#<id>INFLIGHT / deadlineAt
DomainDOMAIN#<host>META——

Three design points

Deployments live under their project. The sort key embeds an ISO timestamp, so Query(PK, ScanIndexForward: false) returns them newest-first with no sorting, no filtering, and no extra index. LastEvaluatedKey gives free cursor pagination.

GSI1 provides lookup by opaque id. Entities are addressed by id from the API but stored under their parent for list queries; GSI1 bridges the two.

GSI2 is a sparse in-flight index. gsi2pk = "INFLIGHT" is written only while a deployment is non-terminal and REMOVEd on every terminal transition. The index therefore holds only live builds — a handful of items. The sweeper queries it in time proportional to stuck deployments, not all deployments.

The likely bug

Every terminal transition must REMOVE gsi2pk, gsi2sk. Forgetting it in one code path leaks an item into the sparse index permanently, and the sweeper reprocesses it forever. This gets a dedicated unit test per transition.

The critical write

UpdateItem
  Key: { PK: "PROJECT#prj_7f3a", SK: "DEP#...#dep_9c21" }
  UpdateExpression:    SET #s = :provisioning, startedAt = :now, taskArn = :arn
  ConditionExpression: #s = :queued          <- exactly one winner

Consistency

  • Authorization reads use ConsistentRead: true. A stale read there is a security bug.
  • Dashboard reads are eventually consistent. Half a second of staleness is fine.
  • GSI reads are always eventually consistent — the sweeper re-checks the base item with a consistent read before acting.

Not stored here: build logs (CloudWatch, referenced by logStreamName), artifacts (S3, by artifactPrefix), secrets (Secrets Manager and SSM).

03 · API

Contract

Sessions, not JWTs

Opaque random tokens stored hashed in DynamoDB. Revocation actually works and there is no signing key to leak; at this scale the extra read costs nothing.

The authorization rule

Load the project with ConsistentRead: true, compare ownerId to the caller, and return 404, not 403, on mismatch — so the API never confirms the existence of another user's resources. Enforced in one middleware, not per-handler.

Triggering a deployment

POST /projects/{projectId}/deployments
{ "branch": "main", "commitSha": null, "idempotencyKey": "cli_2026-09-01_a1b2" }

202 Accepted
{ "deploymentId": "dep_9c21", "status": "QUEUED",
  "hostname": "dep-9c21.example.com", "createdAt": "..." }

If commitSha is null the API resolves the branch head through the GitHub App before creating the record, so the deployment is pinned to an immutable SHA rather than a moving branch.

The idempotencyKey is scoped to the project; a repeat within 24h returns the original deploymentId. This protects against double-clicks and client retries, which are far more common in practice than duplicate SQS deliveries.

Repository URL is not accepted here

It lives on the project, was validated at project creation, and is read server-side. Accepting it per-deployment would let a caller point an existing project at an arbitrary repository.

Repository URL validation

Parse with new URL(), never a regex, then assert all of: protocol is exactly https:; hostname is exactly github.com (allowlist, not suffix match — github.com.evil.io must fail); no user:password@; path matches ^/[\w.-]+/[\w.-]+(\.git)?$; no . or .. segments. Store parsed owner and repo as separate fields and never re-parse the raw string.

Path security

No endpoint accepts a path. The server derives every S3 key from IDs, so path traversal is prevented by construction rather than by filtering. Pagination cursors are HMAC-signed so clients cannot forge a key into another partition.

Quotas

LimitValueEnforced by
API requests20/s burst, 5/sAPI Gateway throttling
Concurrent deployments per user2DynamoDB conditional counter
Deployments per user per day50DynamoDB counter with TTL reset

The concurrency cap is not a politeness feature. It is the primary bound on how fast a malicious repository can burn AWS credits.

04 · Build contract

The untrusted interface

What the container must NOT have

This list is the security design. It is worth more than the diagram.

  • No GitHub token, SSH key, or any GitHub credential
  • No DynamoDB, SQS, Secrets Manager or SSM permissions of any kind
  • No s3:GetObject on the artifact bucket — write-only, own prefix only
  • No s3:DeleteObject anywhere
  • No production database, cache, or internal service to reach — none exist

The complete task role, in full:

s3:PutObject      -> arn:aws:s3:::platform-artifacts-prod/${ARTIFACT_PREFIX}*
logs:PutLogEvents -> the deployment's own log stream
(nothing else)

ARTIFACT_PREFIX is server-generated and never client-influenced. The container cannot write outside its own prefix even if fully compromised — which is what makes “immutable artifacts” actually true rather than aspirational.

Extraction safety

Zip-slip — commonly missed

Reject any entry whose normalised path escapes the destination. Reject symlinks and hardlinks pointing outside the root. Enforce the decompressed-size cap while streaming, not after — a 1 MB tarball can expand to 100 GB. Enforce a file-count cap during extraction.

Build execution

Lifecycle scripts run. That is the entire point of the platform, and it is why the container is disposable. Adding --ignore-scripts would break most real projects and be security theatre, since npm run build executes arbitrary code seconds later regardless.

  • Runs as a non-root user inside the container.
  • NODE_OPTIONS=--max-old-space-size set below the task memory limit, so Node throws a catchable heap error before the kernel OOM-kills the task and destroys the logs.
  • No shell: true, no interpolation of user-controlled values. Build commands come from a fixed table keyed by detected framework — never from package.json.

Exit codes

Limits

LimitValueEnforced where

Two independent timeout mechanisms are required. The watchdog handles a slow build; the external StopTask handles a wedged one that cannot kill itself. Relying on either alone leaves a case where a task runs until something else notices — which on Fargate means “until you notice the bill”.

Artifact upload

Bounded concurrency — 8 parallel PutObject calls — not one-by-one, and not unbounded. Streaming, never buffering whole files. Content-Type set from extension; getting it wrong means the browser downloads your HTML instead of rendering it. Fingerprinted assets get max-age=31536000, immutable; HTML gets max-age=0, must-revalidate.

Logs are one JSON object per line, capped at 8 KB per line and 10 MB per build, with STATUS_TOKEN and SOURCE_URL redacted — build tools print their environment more often than you'd expect.

05 · Threat model

Assume every build is a compromise

The premise of the whole system is that we execute code written by people we do not trust. Design rule: assume every build is a successful attacker, then ensure the blast radius is one disposable sandbox.

Assets, ranked

  1. The AWS account
  2. The GitHub App private key — grants read on every installed repository
  3. Other users' artifacts and deployment metadata
  4. The credit balance — finite and exhaustible, uniquely relevant here
  5. Platform availability

Accepted risks

Stating these plainly is stronger than pretending they're solved.

  1. Unrestricted egress from the build container. Needs a proxy or Network Firewall (~$300/mo). Mitigated by there being nothing worth exfiltrating.
  2. No container-escape defence beyond Fargate's own isolation.
  3. No dependency scanning. A malicious npm package gets the same nothing a malicious repo gets.
  4. No WAF on the API. ~$8/mo, deferred; API Gateway throttling is the interim control.
The credibility item

Seven security tests belong in CI as executable tests, not as a checklist — a fixture repo that probes for AWS credentials, one that writes outside its prefix, a crafted zip-slip tarball, an infinite loop, a cross-user access attempt, three malicious URLs, and an injected branch name.

This is what separates documented security from implemented security, and it is the single highest-value credibility item in the project. Each test must also demonstrably fail when its control is removed — a test that has never failed is not a test.

07 · Roadmap

Build by risk, not by layer

Correction to the original build order

The original plan started with “Step 1: create the React dashboard.” That is backwards, and it's the most common way projects like this die.

The dashboard is the part you already know how to build. The parts that can actually defeat you are: does the Fargate task launch and report correctly, does the IAM scoping really hold, does CloudFront actually rewrite a host into an S3 prefix. Build the dashboard first and you get three weeks of visible progress followed by discovering the hard part doesn't work. Build the build plane first and you find out on day four, when changing course is cheap.

Rule: nothing gets a UI until it works from the command line.

Sequencing rules

  1. Terraform from M0. Retrofitting IaC onto click-ops costs more than writing it first, every time.
  2. One vertical slice before any breadth. One repo, one framework, one user, one domain.
  3. The UI is last. Everything through M5 is exercised with curl.
  4. Security is M5, not “later”. Later does not arrive, and the security story is the most valuable thing this project says about you.
  5. Write the ADR when you make the decision. The reasoning is gone within a week.

M9's video matters more than one more feature — most people reviewing this will watch 60 seconds and never run it.

08 · Testing

Testing an async distributed system

Genuinely harder than testing a CRUD app, and “I'll check CloudWatch” is not a strategy. Decide this before writing code.

Know this before you rely on LocalStack

LocalStack Community does not support ECS/Fargate, CloudFront, CloudFront Functions, or KeyValueStore — all Pro-only. It covers the control plane and nothing else.

And it does not enforce IAM. Every policy in this project will appear to work locally regardless of whether it is correct. All IAM assertions must run against real AWS.

The test worth writing first

test: duplicate SQS delivery launches exactly one task
  - seed a QUEUED deployment in LocalStack DynamoDB
  - invoke the dispatcher twice concurrently with the same deploymentId
  - assert: RunTask called once; final status PROVISIONING;
            the losing invocation returned cleanly without throwing

That single test is the strongest evidence for the idempotency claim, and it runs in milliseconds.

The hardest things to test

The reconciler and sweeper exist for failures that are hard to cause on purpose. Cause them directly rather than waiting.

PathHow to trigger it deliberately
Reconciler on OOMFixture that allocates past the memory limit; assert OUT_OF_MEMORY from exit 137
Reconciler on external killaws ecs stop-task mid-build; assert it doesn't stay BUILDING
SweeperInsert a deployment with deadlineAt in the past; invoke; assert FAILED
KVS driftWrite DynamoDB without writing KVS; assert the sweeper repairs it

The specific bug to guard against is a deployment stuck non-terminal forever. It's the most likely real-world failure and the least likely to be noticed, because nothing errors — the UI just spins. Add a nightly assertion that no deployment has been non-terminal for over an hour.

On tsc vs esbuild

The original document was unclear here. Use both, for different jobs: tsc --noEmit for typechecking, esbuild for bundling Lambda handlers. They aren't alternatives — esbuild strips types without checking them, and tsc is slow at emitting. Not a controversial choice, just the standard split.

Not tested, deliberately

CloudFront caching behaviour (it's AWS's code), React component internals, Terraform beyond validate and plan, and load/performance — there is no load, and saying so is better than a meaningless k6 run.

Decisions

Architecture decision records

Written at the moment the decision is made, not retrospectively. “Alternatives considered” is the section that carries the weight — an ADR without it is just a note.

ADR-0002Split the system into a control plane and a build plane

One boundary, everything arranged around it. Assume every build is a successful compromise and make that survivable.

Rejected: building on the API host (RCE as a feature); Lambda (15-min ceiling, reused execution environments); long-lived EC2 workers (state leaks between builds); CodeBuild (solves isolation, but buying it defeats the point of demonstrating it).

ADR-0003SQS dispatcher plus EventBridge reconciler

Fills the empty “orchestrator” box. Dispatcher claims and launches without waiting; reconciler catches tasks that die without reporting; sweeper catches tasks that vanish silently.

Rejected: Step Functions runTask.sync — genuinely good and would remove the reconciler entirely, but .sync hides exactly the problem worth demonstrating. Reconsider later; the cost is pennies.

ADR-0004The control plane fetches source; the container gets no GitHub token

Trusted side pulls the tarball with a GitHub App installation token and hands over a 15-minute presigned S3 URL. Size cap enforced before any container starts.

Rejected: a short-lived token in the container — “short-lived” means an hour, exfiltration takes a millisecond.

ADR-0005Edge routing via CloudFront Function and KeyValueStore

Sub-millisecond host-to-prefix rewrite with no origin round-trip. Rollback is a PutKey, and immutable prefixes mean no cache invalidation ever.

Rejected: Lambda@Edge with a DynamoDB lookup — one source of truth, but 30–80ms on every asset request. Wrong tool for a hot path this simple.

ADR-0006Static output only in the MVP

Keeps the security model coherent: untrusted code runs only during a bounded build, never as a long-lived request handler.

Rejected: silently accepting Next.js and deploying .next/static — produces a broken site and a confusing failure, the worst of the three outcomes.

ADR-0007Public subnet, no NAT Gateway

$0/month instead of $32. Zero inbound rules; free gateway endpoints for S3 and DynamoDB. The private topology lives behind a Terraform flag and is demonstrated temporarily.

Rejected: interface endpoints without NAT (~$29/mo — worse than the NAT it replaces, and npm is still unreachable); a NAT instance (single point of failure that teaches nothing this project needs).

ADR-0008Single-table DynamoDB with a sparse in-flight index

Every access pattern is a GetItem or Query. No Scan anywhere. The sweeper stays cheap forever regardless of history size.

Rejected: a scheduled table scan — simpler to write, unbounded in cost, and misses the chance to show that sparse indexes exist.

ADR-0009The container reports status through a scoped API, not DynamoDB

Granting the untrusted plane dynamodb:UpdateItem — even with LeadingKeys — scopes to the project partition, so a compromised build could mark another deployment DEPLOYED or repoint its artifact prefix. Instead: a per-deployment 256-bit token, stored hashed, expiring at the deadline.

Result: the untrusted plane has zero write access to control-plane state, and the trust boundary becomes trivial to describe — worth more than the code it costs.
